# 开发计划

> 这份文档回答四件事：**还差哪些功能**、**它们怎么互相配合**、**要调什么工具**、**开发者要准备什么环境**。
> 更新于 2026-11-21，对应 `v0.1.4` 之后的代码状态（B、C 两个队列已清空）。

---

## 一、四层结构

依赖只能从上往下，下层不许反向依赖上层：

```
┌─ 交互层 ── 三栏界面 · 编辑器 · 数据面板 · 设置 · 对话栏
├─ 智能层 ── 模型接入 · 上下文装配 · 工具调用 · 集群调度 · 讨论编排 · 对话压缩
├─ 读写层 ── 文件工作区 · 书库检索 · 台账同步 · 一致性引擎 · 导出转换 · 书库迁移
└─ 地基 ──── 书库格式（雪风卷宗 v1）· 单一事实来源 · Git 留痕 · 通道契约
```

地基不稳上面全塌，所以先看第二节的完成度，再谈还差什么。

## 三、功能怎么配合

### 链路一：写作 → 落盘 → 留痕

```
编辑输入 → 1.2 秒防抖 → 原子写盘（0.06ms）
        → 提交策略：内容没变跳过 / 距上次<20秒只写盘 / 到点或手动则 git commit（约140ms）
        → 标记待同步 → 停手 N 秒 → 台账自动同步 → 一致性检查 → 看板与数据面板刷新
```

### 链路二：对话 → 工具 → 事实

```
一句话 → 选模式（对话/讨论/计划）→ 按模式过滤工具集
      → 模型回 tool_calls（不支持就退化成约定 JSON 块）→ 工具执行
         · 只读工具走只读投影（内存现算，不落盘）
         · 写盘工具先要确认；改文件另有四道护栏（越界/唯一命中/不许大幅缩短/确认）
      → 结果回灌 → 模型收口 → 过程卡里留下痕迹
```

### 链路三：计划 → 确认 → 执行

```
计划模式 → 建计划表（末列「执行结果」留空）→ 界面显示计划卡 → 作者确认
        → 服务端逐步执行：成功写「成功：…」/ 失败立刻停并标「未执行」→ 一条总结 + 一个 Git 提交
```

### 链路四：事实 → 界面

```
Markdown 正本（唯一事实来源）
   ├→ 解析器 → 看板 → 数据面板（人看）
   ├→ 只读投影 → agent 查（机器看）
   └→ 一致性引擎 → 跨表矛盾 → 可补齐的自动补 / 需裁定的等人
```

### 红线

| 允许 | 禁止 |
|---|---|
| `01` 调 `05/06/09/10/12` | `10` 反向依赖 `02` |
| 界面只通过 `桥` 调后端 | 界面直接读磁盘 |
| 各模块都走 `11 文件工作区` 写盘 | 模块自己 `fs.writeFile` |
| 路径从 `10 书库检索/书库布局.ts` 取 | 硬编码台账路径 |

## 四、还差什么（按依赖排序）

### 第 1 批：内容层（不是代码，是书里的东西）

| 事项 | 谁做 |
|---|---|
| 知情台账填起来 | 总控：逐条读正文，填不了的留空并报告 |
| 一致性「需裁定」逐条处理 | 总控：数据错误就改，创作决策只建议 |
| 大纲里写 `计划总章数：N` | 比扫全文猜章号准；可由总控写入 |

### 第 2 批：多视角 Agent（见第六节，待拍板）

### 第 3 批：交付与体验

- 自动更新的完整演练（装旧版 → 发新版 → 自动更新）
- 首次启动引导（选书库 / 配网关 / 介绍一致性面板）
- 讨论结果一键接成开写包

### 明确不做

- 代码签名（自签名拦不住 SmartScreen）
- 云同步、多人协作、移动端
- 向量检索（事实要权威值，不要相似度）

## 五、工具栈

| 层 | 工具 | 为什么选它 |
|---|---|---|
| 运行时 | Node.js 20+ | Electron 自带 |
| 桌面壳 | Electron 33 | Tauri 要 Rust 工具链 |
| 界面 | React 18 + Vite 5 | 生态稳、热更新好 |
| 打包 | esbuild | 比 webpack 快一个量级 |
| 安装包 | electron-builder（NSIS） | 不自己写 NSIS 脚本 |
| 数据 | 纯文件：Markdown + YAML frontmatter | 数据库会和文件不一致 |
| 版本 | Git（书库本身就是仓库） | 每次写入可回滚 |
| 校验 | 自写 `书库校验.ts` | 通用校验器不懂业务契约 |
| 测试 | 自写回归 41 条 | 要快、离线、少依赖 |
| 渲染 | 自写 Markdown + 手绘 SVG | 引库带来体积与安全面 |
| 图标 | Lucide（只内联 path） | 零运行时依赖 |
| 验收 | headless 浏览器 + CDP | Electron 在无桌面环境起不来 |

刻意不引入：状态管理库、UI 组件库、ORM、i18n 框架、CSS-in-JS。

## 六、多视角 Agent 提案（待拍板）

作者的设想：把「写小说的 AI」换成**多个第一人称 AI**——每个角色一个、每个设定一个、每个伏笔一个、世界一个，最后由总控调度。

### 判断：方向对，但不能让每个 AI 都去「写」

| 层 | 谁 | 职责 | 第一人称 |
|---|---|---|---|
| 视角层 | 角色 / 设定 / 伏笔 / 世界 各一个 agent | 说「我这个角色此刻会怎么反应、说什么、想什么」，守着档案不越界 | **是** |
| 调度层 | 总控 | 决定本章谁在场、问谁、谁先谁后，把多方意见收敛成一件 | 否 |
| 成文层 | 执笔（唯一） | 把视角层的意图写成统一语感的正文 | 否 |

**为什么不能让角色 AI 直接写正文**：十四个第一人称各写一段，文风必然碎裂，读起来像拼贴。角色给「料」，执笔给「文」。

### 三个必须解决的机制问题

1. **信息闸（杀手级组合）**：角色 AI 只能看到它此刻知道的——直接读知情台账 + 阅读游标，超出章节的秘密不下发。于是它天然不剧透、天然不用上帝视角。
2. **成本**：唤醒 14 个角色 = 14 次请求。必须按需唤醒：只唤本章在场的人（出场追踪能算），设定/伏笔按本章涉及唤醒。粗估一章 3–5 个 agent 可持续。
3. **一致性**：从「跨表对齐」升级成「跨主体对齐」——角色说「我左手受伤了」而属性变更表没记，就该报出来。

### 已有基础

| 基础 | 用途 |
|---|---|
| `06 成员目录` | 已是「角色 → agent」映射，扩一下就是视角层 |
| `05 集群调度` | 并发池 + 阵容选择，可做「本章唤醒谁」 |
| `知情台账` + 阅读游标 | 信息闸的数据基础（缺的是数据） |
| `09 一致性` | 从跨表扩展成跨主体 |
| `13 会话簿` | 每个 agent 的记忆延续，跨章不丢人设 |

### 落地顺序

1. 最小闭环：一章只唤醒 2–3 个在场角色，各说会怎么做，总控收敛，执笔成文；与现有派活共存、开关切换。
2. 补信息闸（按知情台账裁剪上下文），验证不剧透。
3. 扩到设定/伏笔/世界主体，一致性升级成跨主体。
4. 最后才谈视角层直接产出正文候选，即使那时也保留执笔统一润色。

**风险**：唤醒成本随角色数线性涨；角色 AI 容易抢戏或替作者做决定；人设漂移要靠会话簿 + 档案双锚。

## 七、开发者要准备什么

| 需要 | 版本 | 说明 |
|---|---|---|
| Node.js | 20 LTS 或 22 | `node -v` |
| Git | 近两年版本 | 配 user.name / user.email |
| 编辑器 | VS Code | ESLint、Prettier、中文包 |
| 浏览器 | Edge / Chrome | 预览与 CDP 验收 |
| 磁盘 | ≥ 2GB | node_modules 约 600MB |

第一次跑起来：

```bash
git clone https://github.com/snowwind621/snowwind-novel-agent.git
cd snowwind-novel-agent && npm install
npm run build && npm run 预览      # http://127.0.0.1:5178
npm start                          # 或双击 启动.cmd 开桌面窗口
```

要配三样：网关地址/密钥/模型（设置 → 模型）、书库位置、国内打包镜像 `ELECTRON_BUILDER_BINARIES_MIRROR`。

## 八、怎么验证

三层缺一不可：

| 层 | 手段 | 耗时 | 抓什么 |
|---|---|---|---|
| 类型 | `npx tsc --noEmit` | 3 秒 | 接口对不上、字段拼错 |
| 逻辑 | `npm run 回归`（41 条） | 约 1 秒 | 解析、命名、伏笔状态机、导出、设置真生效 |
| 界面 | headless + CDP 真点 | 1 分钟 | 布局错位、点不到、白屏 |

造数据：假网关（3077，可吐 tool_calls 分片 / 报 500 / 超时）+ 回归脚本自造样本书库。**别打用户真实网关**（除非明确要跑真实链路）。

## 九、发布流程

```
改代码 → 补 CHANGELOG 未发布 → build / tsc / 回归 / 整洁 → 提交 → push
        → 攒够一个主题 → 改 version → npm run 打包 → git tag + push → 建 Release
        → node "19 打包发布/传更新包.mjs" vX.Y.Z（自动更新靠这三个文件）
```

节奏：日常进 `[未发布]`；发版先发补丁号；次版本只在真里程碑动；同一天最多一次。

## 十、协作规则

| 规矩 | 为什么 |
|---|---|
| 每个任务声明写域 | 两人改同一文件必然互相覆盖 |
| 有依赖的用 blocked_by 排队 | 先定接口再做界面 |
| 长文件禁止「读取限行 + 整文件写回」 | 被坑过三次（CHANGELOG 139→37 行、样式.css 993→749 行） |
| 提交前先看 `git status` 再写信息 | 否则会把队友改动带进自己的提交 |
| 功能改动必须补 CHANGELOG | 否则半年后没人知道为什么这么写 |

## 十一、已经踩过的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| Electron 窗口不出现也没报错 | `ELECTRON_RUN_AS_NODE=1` | 启动前清掉 |
| 页面白屏无报错 | 构建换哈希、浏览器缓存旧 HTML | 预览服务已加 no-store；应急 `?清缓存=1` |
| 每次保存弹一堆黑窗口 | git 子进程没加 windowsHide | 已在 Git提交.ts 修 |
| 打包报 Access denied / EOF | 去 GitHub 下 Electron / NSIS | 配 electronDist + 镜像 |
| `fs.cpSync` 崩溃（0xC0000409） | Node 24 / Windows | 自写递归拷贝 |
| 数据面板整页白屏（React #310） | 三个 hook 写在提前 return 之后 | hook 全部前置 |
| 工具回执说「完成」实际失败 | 底层 成功:false 没往上带 | 如实回执失败并带原因 |
| 自动更新静默失效 | latest.yml 文件名与实际产物不一致 | 打包脚本收尾对齐 |
| 端口 5178 被占 | 旧进程没退 | `npm run 预览:重启` |
| 想抄别人代码 | nb-story 是 AGPL；OpenFic 是 Apache-2.0 | 只借设计，或按许可注明出处 |
