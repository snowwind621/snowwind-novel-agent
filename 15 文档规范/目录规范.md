# 目录规范

## 命名

- 顶层源码目录：`序号 + 空格 + 具体方向`，例如 `10 书库检索`。
- 序号只用一次，不复用，删掉一个模块后它的号就空着。
- `package.json` 的 `name`、代码里的标识符用英文（`setting-archive`、`library-index`），避免踩工具链的坑；**目录名**保持中文。
- 一个文件夹只能负责一个方向；一个代码文件只能负责一个功能。文件名就是它的职责说明书。

## 书写约束

- 每个源文件开头一行注释，写清「只负责一件事：……」。写不清，说明它该拆了。
- 跨模块只通过 `03 进程桥接/通道.ts` 的契约或明确的函数签名打交道，不靠全局变量。
- 不写「以后可能会用到」的参数与分支。

## 书库目录（被读取的项目，不是本工程）

```
<书库根>/
  书卷.yaml              格式版本 / 书名 / 作者
  正文/                  正文正本
    第一卷/              卷是目录（第一卷、第二卷…）
      第001章 章名.md     一章一个文件，编号即章号
  设定/                  稳定设定，一份设定一个文件
    世界观/ 人物/ 地点/ 物品/ 势力/ 制度/ 事件/ 规则/ 备注/
    面板镜像.json         旧格式残留，软件不读（迁移旧书库时才读旧镜像）
  台账/                  七册：时间线 / 出场追踪 / 关系线 / 属性变更 / 队伍状态 / 物品台账 / 承诺台账
  情节/                  分卷大纲、细纲、开写包
  校验/                  校验与放行依据
  留痕/                  历史口径（唯一允许写旧值的地方）
  考据/                  原作考据，不作写作依据
  导航/                  事实归属表
  讨论/                  派活记录与争论，不作依据
```

## 提交纪律

每次改动都走同一条流水线，不许跳步：

1. **先写更新日志**：在 `CHANGELOG.md` 的「未发布」里记一条，写清改了什么、为什么。
2. **再跑整洁检查**：`npm run 整洁`，五项全绿才继续。
3. **然后提交**：`.githooks/pre-commit` 会再扫一遍暂存内容，密钥/大文件/日志一律拦下。
4. **最后推送**：`git push`。

新增文件前先问三句：**它是正本还是产物？属于哪个序号目录？会不会泄漏密钥或个人路径？**
产物（`dist/`、日志、导出文件）一律进 `.gitignore`，不进库。

## 版本与发布纪律

**提交照常，发布要攒。** 每次改动都提交、都推送，但 GitHub Release 不跟着提交走。

- **什么算一次发布**：攒够一个完整主题（比如「改写循环 + 开写包 + 书架」这种一组能力），或者有破坏性变更。
- **版本号怎么走**：`0.x.y` —— `x` 只在有完整能力组或有破坏性变更时加一；`y` 留给修 bug 与打磨。
  **同一天内不连升版本**，更不许把版本号当计数器用。
- **发布动作**：把 CHANGELOG「未发布」整段搬到新版本号下 → 打 tag → 建 Release（标题与正文直接用那一段）。
- **不做的事**：每做一个功能就发一版；发了又删；为了显得活跃而发版。

日常提交的信息里写清楚改了什么就够了，版本号只对「使用者需要知道」的节点负责。
